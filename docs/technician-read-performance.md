# Technician reads

`technicianDay` and `technicianJob` keep the existing OWNER/TECH API boundary. No new query operation, table, GSI, stream, or backfill is introduced. Gen2 already creates Job relationship indexes `gsi-Route.jobs` and `gsi-Customer.jobs`; the former filtered `Job.list` scans did not use them.

The day now reads every matching route page, including duplicate routes, and queries each route's existing Job index with concurrency three. Strong current Job reads verify route membership and assigned technician before customer context is exposed. Stops with conflicting assignments remain withheld from TECH, flagged for OWNER, and recorded in durable `ROUTE_MISMATCH` work. An unconfirmed case write fails visibly so the day cannot appear clean while a stop has disappeared. Customer reads are limited to the visible stops and visit fields, with concurrency four.

The technician identity uses the existing userSub index and strong current identity facts. Authorization and licence facts are reused only inside one request; each new request and action rechecks its own authority. Inactive technicians are refused, lapsed technicians can review only their own completed records/reports, and lapsed review returns no other-visit history, lineage, or catalog. A licence GraphQL page error fails closed rather than falling back to a legacy credential.

The first job packet exhausts only that customer's narrow Job metadata. Its relationship index is hash-only, so a first-page limit cannot honestly mean the most recent visits. Complete metadata is sorted before choosing six recent contexts. Prior report hydration has concurrency three. A separate `HISTORY` view evaluates at most twenty customer-index entries per page, preserves empty-page continuation, and allows access to dated and undated visits in every lifecycle. The UI deduplicates the initial context and exposes further pages explicitly. Loaded pages are sorted by date; the native hash-index cursor does not promise a chronological global page boundary. Its versioned cursor binds caller, job, and current customer, and every page reauthorizes assignment and licence.

Report reads query the existing jobId index and strongly verify selected current source rows. A `CURRENT` view refreshes job/customer/report essentials after writes without reloading catalog, customer history, or lineage. Save and finalize pass the confirmed report ID into that view, which reads the exact source row even before a new report appears in its index. Missing or unverified report/context reads are marked unavailable and retryable; they are not treated as an empty report. Existing product metadata is retained through thin refreshes, with no cross-request catalog cache that could hide a revoked label approval.

Lineage walks the already verified same-customer metadata, avoiding a sequence of single Job reads and the previous silent five-attempt cutoff. Missing/cross-customer pointers or cycles are explicitly unavailable. No new reconciliation or repair action is performed by these reads.

The report write order remains save draft → end application → finalize → authoritative refresh. The existing server stamps, idempotency, finalization checks and durable effects are unchanged. UI read generations and the existing auth-cache scope fence late results across job changes, permission changes, and same-user logout/login. Existing login write scopes stop old-login callbacks from continuing mutations or clearing a new-login draft; ordinary token renewal does not end a login's write scope. Unmounted editors cannot clear a newly mounted editor's local draft.

## Deployment and verification

Deploy the backend first: the existing `technicianJob` query gains optional `view`, `historyToken`, `historyLimit`, and `reportId` arguments. Its default response remains the full packet for older clients. The CRM outputs gate requires those exact arguments before building. Added Lambda permissions cover only Query on the four existing Job/Technician/ServiceReport indexes and selected Get/BatchGet on their source tables. Runtime table names use the retained backend's SSM API-ID binding, not the GraphQL endpoint hostname. No data/index activation migration is required.

The actual migration assembly checks retain the existing nine Job GSIs, unchanged resource/resolver counts, exact new read actions, reference closure, pause coverage and retention protections. Backend tests cover current membership, stale/ambiguous identity links, duplicate-route pagination, durable-case failures, licence errors, complete customer sorting, continuation binding, report verification and report concurrency. Render tests cover preserved newer typing, write/refusal order, missing new-context report/PDF removal, recovered findings, late job/history/current responses and same-sub login ABA cases. These are offline proofs; no live technician query is invoked, because a day read may open durable work cases. No production latency claim is made before an authorized read-only-safe benchmark is available.
